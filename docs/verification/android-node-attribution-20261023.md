# Android: идентичность маршрута после обновления профиля

23 октября 2026. Работа продолжает наблюдение DE→NL из
[предыдущего прогона](android-blocker-idle-20261023.md). Его причина ещё не
установлена: исправление ниже устраняет отдельно воспроизведённый дефект.
Личный VPN, маршруты, DNS, PF и службы Mac не изменялись. Используется только
ранее явно разрешённый владельцем Mi A1, Android9/API28, user0.

## Воспроизведение и исправление

`/devices` читается до выдачи профиля. Выдача может изменить размещение
установки. Раньше новый профиль обновлял endpoint, но сохранял старый `nodeId`.
В итоге реальный конфиг и метаданные устройства могли описывать разные узлы;
старый идентификатор также исключал маршруты нового размещения. Общий
`profileEndpoint` предпочитал метаданные конфигу, поэтому диагностика могла
показывать адрес, который native backend вообще не использовал.

- Endpoint теперь берётся из конфига, поступающего в native backend;
  legacy-профили без строки Endpoint сохраняют прежний fallback.
- Fresh, unchanged и staged PSK ответы используют одинаковое обновление
  метаданных. При смене endpoint старый `nodeId` становится неизвестным;
  новый узел не угадывается по адресу, поскольку адрес может быть relay.
- Старый hot cache с противоречащим endpoint не может блокировать маршруты
  актуального конфига своим старым `nodeId`. Ограничения device, location,
  protocol и срока действия политики сохранены; правдоподобный, но другой
  идентификатор узла с совпадающим endpoint по-прежнему отсекает кандидатов.
- Формат API, ключи, схемы хранения и Android native engine не меняются.

RED/GREEN тест воспроизводит устаревший узел и endpoint на прежнем коде.
Интеграция исполняет настоящий managed profile flow, parser и route engine;
проверены fresh/unchanged/hot-cache, сохранение корректного узла и отказ
маршрутам другого устройства/локации. Лишней выдачи профиля или запроса
списка устройств нет. Исправлен старый telemetry fixture, который менял
только метаданные порта, оставляя прежний порт в native config.

## Физическая приёмка 1.0.76

Обновление поверх1.0.75 сохранило firstInstallTime, вход и выбранный Noord.
Из установленного пакета извлечён APK, его SHA совпал с проверенным артефактом.
Обычный UID подтвердил одинаковый HTTPS/STUN выход физического nl-awg3,
отличающийся от direct baseline. Это сопоставление реального IP с inventory,
а не вывод только из GeoIP. UI показывал «Соединение защищено» и Noord.

Сценарий Mullvad с шестью уникальными system-DNS именами прошёл6/6:
DNS187–532мс, полный запрос636–1689мс. Все authoritative resolver IP совпали
с HTTPS в том же receipt и параллельными ordinary-UID HTTPS/STUN; direct IP
другой. Флаг `mullvad_dns=false` ожидаем для VEX и не считается утечкой.

Wi-Fi loss/rebind: в исправленном разборе только `Current Networks` VPN118
остался без WIFI/MOBILE, затем WIFI119 сменился на120 при том же VPN118.
После возврата сети и5с выдержки HTTPS/STUN/DNS прошли через прежний NL.
Первый сценарий ошибочно считал историю dumpsys текущими сетями; его assertion
и ранние тайм-ауты после возврата Wi-Fi сохранены как неудачный прогон.
Отдельный recovery control подтвердил все три протокола до повторного опыта.
Это не измерение минимального recovery time и не приёмка LTE handover.

При Screen OFF/Dozing30,181с обычный foreground observer получил HTTPS,
STUN и DNS через VPN; после Awake все три повторно прошли через тот же NL.
Этот observer удерживает CPU для пробы: kernel suspend/deepDoze не подтверждён.

Reboot завершён за44,160с. После app-open вход и Noord сохранены;
проверка до явного подключения показала direct HTTPS/DNS. Затем обычное
подключение успешно: HTTPS/STUN/DNS через тот же NL. Второй authoritative
DNS batch также6/6, resolver совпал с собственным HTTPS и post-boot VPN.
Автоподключение и headless/boot lockdown этим опытом не подтверждены.
В шести успешных ordinary-UID наборах (до/после DNS, recovery control,
повторный rebind, после сна и после reboot) DE-выход не наблюдался.
Внутри Screen OFF тоже подтверждены три протокола и прежний NL.
Исторический переход DE→NL по этим данным причинно не объяснён; текущие
серверные условия и свежая выдача профиля также могли влиять на результат.

Cleanup PASS: три созданных QA package, test keystore и временный phone UI
файл удалены. Wi-Fi/mobile/airplane/always-on/lockdown/timeout/user0 и исходный

## Предварительная физическая диагностика на 1.0.75

Эти результаты относятся к ранее установленному подписанному APK1.0.75,
а не к исправленным исходникам1.0.76. Первое подключение к Noord не
завершилось. Поздний отдельный sample оказался direct с Sisu в карточке и
тем же PID, без зафиксированного момента перехода или успешного egress.
Причина неизвестна; это не приёмка защиты или доказанный обход VPN.
Попытка нажать «Отключить» тогда отказала из-за неоднозначных UI-узлов и
не выполнила input. Повторная оснастка допускает только вложенные узлы
одной кнопки и отказывает при раздельных элементах.

В отдельном контрольном подключении Noord четыре ordinary-UID sample за
111,484с наблюдали один VPN network и не получили HTTPS/STUN; UDP DNS
сначала истёк, затем возвращал SERVFAIL. UI показывал активную защиту и
ошибку технических работ. Это четыре дискретных наблюдения, не непрерывная
запись пакетов. Прямой STUN не отвечал ещё до VPN и не доказывает блокировку.
После явного «Отключить» прямые HTTPS и DNS восстановились. Оба публичных
API `/healthz` на Mi A1 ответили200 непосредственно до/после прогона.
Одновременного исключённого UID-контроля в этом опыте нет.

В начале диагностики MCP получил503/timeout публичного API и авторизации;
актуальной телеметрии не было. Пять физических узлов были доступны,
failed units0; короткие network-pressure deltas0 не доказывают отсутствие
эпизодических проблем. С origin контейнер/proxy/local HTTPS отвечали200,
публичный DNS-путь —503/timeout. Восстановлением публичного входа занимается
отдельная операторская задача; серверы здесь не перенастраивались.
