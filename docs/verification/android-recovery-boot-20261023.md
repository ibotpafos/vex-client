# Android 1.0.78: выходной узел и защита при загрузке

23 октября 2026. Изолированный Mi A1, Android 9/API28/arm64, user0.
Активный VPN Mac не настраивался. Это приватный кандидат: публикации,
OTA, развёртывания и перезапуски серверов не выполнялись. Штатные запросы
выделенного клиента к API и размещение его собственного peer входят в стенд.

Это был реальный запрос другого размещения во время восстановления.
Предыдущий аудит только `fallback_*` пропускал события `reconnect_*`.
Нельзя восстановить конкретное обновление React/AppState, прервавшее тот
исторический effect. Но на том же hook из исходника 1.0.75 воспроизведён
механизм: обновление каталога, профиля, callback либо уход в фон завершали
наблюдатель, а его асинхронное восстановление продолжало менять native VPN.
Затем `disposed` подавлял принятие результата и обновление карточки.

Hook побайтно совпал с source `ef8e533` из 1.0.75, SHA256
`7b5793b8fcc2228f4891230037dd6795d41150c1e48b711169a749bdd33f6635`.
Десять интеграционных сценариев со старым hook падают, с исправленным проходят;
используется настоящий `recoverVpnConnection`, включая профиль, native,
сохранение локации, UI и владение общей операцией. Ещё четыре теста проверяют
отмену подготовки профиля новым действием пользователя; JVM проверяет
отклонение чужого/пустого набора peer и устойчивость отпечатков.

## Исправление

Таймер наблюдения и уже начатая операция восстановления теперь имеют разные
сроки жизни. Снимок входных данных берётся при проверке; смена ссылок на
каталог/профиль/callback не теряет владельца native операции. Поколение
соединения и сессия ограничивают выдачу профиля, активацию, повторные попытки,
сохранение и принятие результата. Старое завершение не освобождает операцию
нового владельца. Неудача или отдельный выбор локации прекращают непринятый
выход с сохранением AntiLeak; явно выключенная настройка AntiLeak соблюдается.

Android сверяет реальные public keys из UAPI со входным профилем при активации,
повторном использовании и восстановлении. Диагностика содержит поколение и
SHA256 peer/endpoint. На сервере отпечатки вычислены до маскирования транспорта:
десять проверенных узлов имеют десять разных ключей. Первое локальное
хеширование уже замаскированного `REDACTED` исключено из доказательств.

## Загрузка

Единственный объявленный системный Always-on entry point —
`VexBootProtectionService`. Он работает в отдельном процессе, доступен Direct
Boot и использует прежний блокирующий TUN с IPv4/IPv6 default routes и отдельным
неразрешающим DNS. Цикла чтения TUN нет. В этом процессе не запускаются
React/Expo/Sentry, не читаются профили и не сохраняются ключи/токены.

Защита требует двух системных переключателей: «Постоянная VPN» и «Блокировать
соединения без VPN». Вторая закрывает промежутки без TUN, включая остановку
процесса и обновление APK. Системные правила и ограничения split tunneling
описаны в [Android VPN](https://developer.android.com/develop/connectivity/vpn).
В настройках VEX добавлена ссылка с объяснением; на Mi A1 она открывает
настройки VEX в Android. До подключения шлюза интернет обычных приложений
блокируется: нужно открыть клиент и подключиться. Автоподключение при открытии
сохраняет прежнюю отдельную настройку.

## Физическая проверка

- 1.0.76→77→78 сохранили firstInstall, вход, выбор и данные. Обновление 77→78
  выполнялось с Always-on/lockdown: 20 проб, из них 18 во время установки;
  до остановки старого VPN выход был DE, шесть проб были заблокированы,
  прямого выхода в пробах нет. Две отдельные свежие пробы после сверки bytes
  также заблокированы. Первоначальный контроллер исчерпал 20 итераций до
  завершения pull APK; это не непрерывная запись каждого пакета.
- На 78 переход Kern(DE)→Noord(NL) сохранил TUN108. Поколения и оба отпечатка
  сменились с de-kernel на nl-kernel; HTTPS/STUN дали соответствующие физические
  выходы, UDP-DNS и numeric TCP прошли. Имя карточки совпало с результатом.
- Отдельный fault run78 отключил Wi-Fi при подключённом Kern. На211.501с
  физический UI показал «Восстанавливаем», на216.375с выбран Noord; Wi-Fi
  возвращён в `finally`, весь сценарий217.196с. До явного подключения выбранного
  NL интерфейс показывал активную защиту, обычные HTTPS/DNS не проходили.
  Последний допущенный DE peer относился к моменту до этого сценария.
  После явного подключения новое поколение и оба отпечатка соответствовали
  nl-kernel; обычные HTTPS/STUN и DNS подтвердили NL, authoritative DNS6/6.
- В защищённом состоянии retained routing TUN принимал TCP SYN локально.
  `forwardTCP` создаёт endpoint до внешнего dial: успешный `Socket.connect`
  сам по себе не доказывает утечку. Поэтому отдельный обычный UID проверил
  `https://1.1.1.1/cdn-cgi/trace` и `https://1.0.0.1/cdn-cgi/trace` без DNS,
  с default TLS/certificate validation и требованием HTTP200+IPv4 echo.
  Оба запроса были заблокированы; после подключения оба дали HTTP200 и тот
  же NL egress, что HTTPS/STUN. Это парный контроль реальных данных.
  Назначение trace описано в [Cloudflare docs](https://developers.cloudflare.com/fundamentals/reference/cdn-cgi-endpoint/).
- Mullvad authoritative system DNS: 6/6, один resolver совпал с собственным
  HTTPS/STUN VPN egress. `mullvad_dns=false` нормально для VEX и не является
  признаком утечки.
- Потеря Wi-Fi и возврат 106→109 сохранили TUN108; после возврата все четыре
  протокола вышли через NL. При отсутствии Wi-Fi LTE underlay не появился.
- Screen OFF/Dozing30.224с, foreground observer и последующее пробуждение
  сохранили NL. Это не kernel suspend.
- Реальный reboot78 — 44.360с. До открытия VEX main PID отсутствовал,
  блокирующий процесс/TUN работали, Always-on/lockdown сохранились. Boot observer
  стартовал на65.303с; HTTPS/DNS/numeric TCP заблокированы. STUN также отказал,
  но его отказ отдельно не считается доказательством: direct control тоже
  не отвечает на этот STUN. Android `top` показал0.0% CPU в двух измерениях.
- Force-stop78 убрал TUN и main process, системный lockdown остался включён:
  обычный UID не получил сеть и ни один протокол не вышел. После открытия,
  сохранённого входа и явного подключения Noord все четыре протокола прошли NL.
- На77 дополнительно проверены обычное отключение под lockdown и его
  выключение в Android: сначала трафик заблокирован, затем direct HTTPS/DNS/TCP
  снова работают. Интерфейс настройки и переход в системный экран проверены.

Ранние fault-прогоны с обычным `uiautomator dump` завершились без выбора

## Границы

Mi A1 использует FDE (`ro.crypto.type=block`), поэтому FBE до первой
разблокировки не принят. Различия хранилищ объяснены в
[Android Direct Boot](https://developer.android.com/privacy-and-security/direct-boot).
Не квалифицированы реальные LTE/IPv6 uplinks и kernel suspend. Native-bound
DNS/HTTPS canary для автоматической приёмки каждого подключения остаётся
отдельной задачей; лабораторные пробы не превращают handshake в такое обещание.

Подробные receipts, исходники QA и исключённые ранние попытки:
`/Volumes/D/Codex Storage/evidence/vpn-boot-attribution-20261023/`.
Локальные сборочные файлы и caches находятся наD; CI использует временное
окружение GitHub, файлы Android — платформенное хранилище выделенного телефона.
